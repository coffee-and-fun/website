# Coffee & Fun writing style

Sound like a helpful person who knows the product. Be plain, warm, specific, and lightly playful.
Give the reader what they need before adding personality.

See [branding.md](branding.md) for identity and [style.md](style.md) for interface conventions. This
guide covers website and product copy. The more specific drafting workflow in
`tools/blog-automation/write-post.md` still applies to automated blog work.

## Voice

Use “we” for the studio and “you” for the reader. Use “I” in a named author's firsthand account. Do
not invent an experience, quotation, measurement, or customer story to make the voice feel personal.

Prefer short sentences with varied rhythm. Use concrete verbs: write, open, save, build, check,
copy. Contractions are welcome. One small coffee reference or dry aside can carry a section;
repeating “brew,” “sip,” and “magic” in every paragraph makes the brand harder to trust.

Avoid jargon, superlatives, stock introductions, and claims such as “seamless,” “revolutionary,”
“supercharge,” or “the ultimate solution.” Describe what happens when someone uses the product.

## Tone by situation

| Situation            | Tone                              | Example                                                                                         |
| -------------------- | --------------------------------- | ----------------------------------------------------------------------------------------------- |
| Homepage             | Warm and direct                   | “We make apps, browser extensions, and free web tools that make everyday life a little easier.” |
| Navigation           | Brief and familiar                | “Apps,” “Tools,” “Help,” “Support”                                                              |
| Product introduction | Benefit followed by useful detail | “Write Markdown and preview it as you go.”                                                      |
| Help                 | Calm and specific                 | “Open Settings, then choose a theme.”                                                           |
| Empty state          | Explain what can happen next      | “No documents yet. Create one to start writing.”                                                |
| Error                | Clear, responsible, actionable    | “We couldn't save your changes. Keep this tab open and try again.”                              |
| Confirmation         | Brief and factual                 | “Copied to clipboard.”                                                                          |
| Blog                 | Firsthand and evidence-led        | “I tested it with three files. Here's what changed.”                                            |

Examples describe a writing pattern, not a promise that a particular feature exists. Match every
instruction and status message to the actual behavior.

## Headings and actions

- Use sentence case for new headings, labels, and buttons: “Explore apps,” “Read the blog,” “Help
  center.” Preserve product names and the existing signature headline.
- Lead buttons with a verb when they perform an action. Name the result: “Copy link,” “Download
  PNG,” “Save changes.”
- Use destination names for navigation. Avoid several unrelated links all labeled “Learn more.”
- Keep one main idea in a heading. Write supporting detail in a sentence below it when the reader
  needs it.
- Name file formats and platforms accurately. Keep capitalization such as Markdown, GitHub, macOS,
  iOS, PNG, and PDF.

## Plain language

| Replace                                   | With                                                 |
| ----------------------------------------- | ---------------------------------------------------- |
| “Unlock a world of powerful productivity” | “Tools for everyday tasks”                           |
| “Leverage our cutting-edge editor”        | “Write and preview Markdown”                         |
| “Real humans, real fast”                  | “A little help from real people”                     |
| “Oops! Something went wrong!”             | The specific problem and a safe next step            |
| “Click here”                              | The destination or action                            |
| “We value your privacy”                   | What is processed, stored, or shared for this action |

Avoid “just,” “simply,” and “obviously” when explaining a task someone may find difficult. Describe
controls by their visible labels, not only by position, shape, or color. Use “select” when an
instruction should apply to mouse, touch, and keyboard input.

## Punctuation and formatting

Use periods, commas, colons, and parentheses. Prefer them to em dashes and en dashes, which are
prohibited in the existing blog workflow. Use straight quotes in blog Markdown and code. Use
exclamation marks sparingly, and leave them out of errors, billing, and privacy messages.

Keep paragraphs focused. Use lists for steps and genuinely parallel items. Use tables for
comparisons. Avoid decorative emoji in headings; an icon should not replace a visible label.

Use relative links for pages within the website. Check external links before publishing. Write
useful image alternative text instead of repeating the caption or starting every description with
“image of.”

## Evidence and promises

Verify numbers, awards, supported platforms, prices, and dates before publishing. Link to evidence
when it helps the reader assess a claim. Never invent social proof or response-time guarantees. Keep
prices and counts in their maintained data sources where possible.

For privacy, say exactly what the relevant feature does. For accessibility, describe available
controls or testing and its limits. Avoid blanket promises such as “works for everyone,” “100%
secure,” and “fully accessible.”

## Blog and help articles

A blog post should have a specific observation, argument, or useful result. Open on the concrete
thing the author did or discovered. Use screenshots, reproducible steps, logs, or measured results
when available. Separate firsthand findings from inference, and acknowledge evidence that is
missing. End on a worthwhile thought instead of automatically turning the final paragraph into a
sales pitch.

Help articles should solve one problem. Name any prerequisite, give steps in order, describe the
expected result, and explain what to try if it does not happen. The article template supplies the
H1; article bodies start at H2.

The existing automation workflow has additional requirements for article length, links, metadata,
and draft handling. Those requirements are specific to that workflow and should not make product
copy longer.

## Before publishing

Read the text aloud. Check that the action labels match their outcomes, claims have evidence,
instructions match the current interface, and the joke does not slow down the answer. Remove any
sentence the reader would not miss.
